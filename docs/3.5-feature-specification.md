# 3.5 — Feature Specification

**Status:** Draft — pending team approval (amended after implementation review — see `3.2-prd.md` revision note)

## Authentication and goal selection

Registration requires email, password, and password confirmation. Email must be syntactically valid; minimum password length is a decision deferred to Chapter 5 (not fixed here); confirmation must match before submission. Successful registration returns to Login with the entered email preserved. Login prevents duplicate submits while pending, reports invalid credentials at form level, and — only on the first successful login — routes to goal selection before showing the learning path.

Goal selection presents exactly two choices: conversation or TOPIK. It is required before any learning-path content loads. The choice can be changed later from account settings; changing it swaps the displayed path but does not delete progress recorded under the previous goal.

Pages requiring login (learning path, scan/reading practice, progress) redirect to Login if the session is invalid or expired. Password reset, email verification, SSO, and social login are excluded, matching the PRD's non-goals. **Implementation note:** the login screen may display a "Forgot password?" link for visual completeness; it is non-functional in v1 (no click handler, no backend route) — this is intentional, not an oversight.

## Learning path lifecycle

The learning path is an ordered list of vocabulary/grammar items scoped to the user's selected goal. For the conversation goal, items are grouped into named **topics** (e.g. "Chào hỏi & Giới thiệu", "Gọi món tại nhà hàng"); a user can browse topics and see per-topic progress (items learned / total items) before opening a specific topic. Each item has exactly one state: **not learned** or **learned**. The user toggles an item's state directly from the path view; no separate confirmation step is required since the action is non-destructive and reversible.

State persists per user, per goal. If the user switches goals, progress under the previous goal is retained and reappears if they switch back — the "no simultaneous goals" assumption applies to which path is *displayed*, not to whether prior progress is discarded.

## Scan-to-speech flow

**Step 1 — Capture.** The user uploads or captures an image. Accepted formats and maximum file size are a technical decision for a later chapter; this spec requires that an unsupported format or oversized file produce a clear, specific error before any processing is attempted.

**Step 2 — Extraction (OCR).** The system attempts to extract Korean text from the image. On success, extracted text is shown in an editable field — the user can correct OCR mistakes before proceeding, since OCR accuracy is a known v1 risk. On failure (no readable text, unsupported content), the user sees an error explaining that no text was found, the previous image selection is cleared to avoid ambiguity about which image failed, and they can retry with a different image.

**Step 3 — Playback (TTS).** The user triggers playback of the text currently shown in the editable field — meaning if they corrected OCR output, playback reads the corrected version, not the raw OCR output. A single default AI voice is used; there is no voice selection in v1 (voice cloning is explicitly out of scope). While audio is loading, the play control shows a loading state and cannot be triggered again until playback starts or fails. On playback failure (e.g. network error), the user can retry without re-uploading the image or losing the edited text.

**Step 4 — No persistence requirement.** Scanned text and audio are not required to be saved for later replay in v1; each scan is a fresh session.

## AI sentence practice (FR-12)

**Scope boundary (important):** this feature is a bounded, single-turn exercise, not a conversational chatbot. Each submission is evaluated independently; the AI is not required to remember prior submissions in the same session.

**Flow:**
1. The user types one Korean sentence into a text input and submits it.
2. The submit control shows a loading state while the AI evaluates; it cannot be re-triggered until the previous evaluation completes or fails.
3. On success, the response distinguishes two outcomes: **correct** (confirmation shown, optionally with a suggested more advanced phrasing) or **incorrect** (the specific error explained in Vietnamese-friendly terms, plus a corrected version of the sentence).
4. On AI service failure (network error, API error, rate limit), the user sees a clear error and can retry without losing the sentence they typed.
5. The input clears only after a successful evaluation, not after a failed request — so a failed request never loses the user's work.

**Technical note:** intended to call the Google Gemini API (see `3.2-prd.md` assumptions); the exact prompt design and error-handling for API-specific failures (e.g. rate limits) is a backend implementation detail for a later chapter, not fixed here.

## Vocabulary review (FR-13)

**Scope:** available per topic, once the user has studied at least some items in that topic (exact threshold, e.g. "at least 1 item marked learned" vs. "topic fully completed," is an open question — see below).

**Formats (at least these three in v1):**
- **Type the Vietnamese meaning:** shown a Korean word, the user types its Vietnamese meaning. Answer matching should tolerate minor formatting differences (leading/trailing whitespace, case) but does not need to handle synonyms or partial credit in v1.
- **Type the Korean word:** shown a Vietnamese meaning, the user types the Korean word. Same tolerance rule as above.
- **Match the pairs:** a set of Korean words and Vietnamese meanings shown together (e.g. as two columns or a grid); the user pairs each Korean word with its meaning. Correct pairs are confirmed immediately; incorrect pairs are indicated but do not end the session — the user can keep trying remaining pairs.

**Session end:** after all questions in a review session are answered, show a summary: how many were correct, and which specific items to revisit. This summary does not need to feed back into FR-5's learned/not-learned state automatically in v1 — that link (does a review session change an item's learned status?) is an open question, not decided here.

## Admin

**Login and routing.** Admin uses the exact same login form as learners (`Login`, per Authentication section above) — no separate admin URL or login page. After successful authentication, the backend response includes the account's role; the frontend routes `learner` → learning path, `admin` → admin dashboard. This is the only place role is checked for routing purposes in v1.

**Content management (vocabulary/grammar/topics).** A table/list view of topics, each expandable to its vocabulary/grammar items. Create and edit use the same form (a modal or dedicated page — implementation detail, not fixed here) with fields: Korean word/phrase, Vietnamese meaning, topic assignment. Delete requires a confirmation step (destructive, unlike the learner-facing item states in the Learning Path section). Validation: Korean word/phrase and Vietnamese meaning are required; topic assignment is required (an item cannot exist without a topic in v1 — no "uncategorized" bucket).

**User management.** A table of registered users showing at minimum: email, selected goal, lock status. A lock/unlock toggle or button per row. Locking is immediate from the admin's perspective (UI reflects the change right away); whether it force-ends that user's current session or only blocks future logins is a backend decision deferred to a later chapter — this spec only requires that new login attempts by a locked user fail with a clear message.

**Usage statistics.** A dashboard view with at minimum: total users (with a breakdown by goal), and a ranked list of most-studied topics (by number of learners with at least one learned item in that topic, or a similar simple metric — exact calculation is a backend decision for later). No date-range filtering or export is required in v1. An empty state (e.g. "Chưa có dữ liệu") is required when there is no data yet, rather than a blank or broken-looking view.

**Access control note:** this spec assumes route-level role checking (an admin route rejects non-admin sessions) is a backend/architecture concern for a later chapter; the frontend routing described above is a UX convenience, not the security boundary.

## Progress view

Shows counts of learned vs. remaining items for the user's *currently selected* goal only, and can additionally show per-topic progress (learned/total per topic) for the conversation goal, consistent with the topic browsing added in the Learning Path section above. It does not need to show combined or historical stats across goal switches in v1.

## UI constraints

All labels, error messages, and instructional text are in Vietnamese. **UI library: Tailwind CSS with `lucide-react` for icons** (implementation decision made during this chapter, superseding any earlier suggestion of a component library like MUI). This specification does not prescribe exact visual layout beyond what's implied by chosen components — that remains Chapter 4's broader responsibility, but the styling technology itself is fixed here since it's already in use in the codebase. Required regardless of styling choice: a visible, non-blocking loading state for OCR extraction, TTS playback, and AI sentence evaluation; error messages specific enough that a user knows whether the problem was the image, the network, the AI service, or something else; and no silent failures (every failure state described above must be visible to the user).

## Open questions

- Exact threshold for when a topic's vocabulary review unlocks (any progress vs. full completion).
- Whether completing a review session should update FR-5's learned/not-learned state, or remain a separate, non-authoritative practice signal.
- Rate-limit handling specifics for the Gemini API under FR-12 (left to backend implementation in a later chapter).
- Whether locking a user account force-ends their current session or only blocks future logins.
- Exact metric definition for "most-studied topic" in the admin statistics view.
